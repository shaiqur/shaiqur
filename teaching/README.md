# Teaching & Mentoring

**Focus:** Computer Science Education · Software Engineering · Programming · Capstone Mentoring · Research Guidance

Teaching has been a major part of my graduate work at Iowa State University.

I have supported courses ranging from introductory programming to graduate research and senior capstone projects, working with students at very different stages of their computing education.

My approach to teaching is strongly influenced by my background in both **research and production software engineering**.

I want students to understand not only:

> “How do I make this code run?”

but also:

> “Why is the system designed this way?”

> “What assumptions am I making?”

> “How do I debug this when the obvious explanation is wrong?”

> “How does this behave outside my laptop?”

# Introductory Programming

For **COM S 104**, I contributed to course-material and assessment development for introductory Python.

My work included:

* Designing quizzes
* Extending and revising laboratory exercises
* Developing and modifying exam questions
* Improving grading rubrics
* Aligning assessments with learning objectives
* Supporting online course delivery

One challenge in introductory programming is that a student may memorize syntax without understanding the underlying problem-solving process.

I therefore value exercises that require students to reason through:

```text
Problem
  ↓
Break it into smaller tasks
  ↓
Choose a representation
  ↓
Write code
  ↓
Test assumptions
  ↓
Interpret the result
```

The goal is to help students develop a way of thinking that transfers beyond one programming language.

# Software Engineering Education

In **COM S 309 — Software Development Practices**, students move beyond small assignments into larger team-based software projects.

This creates a different set of challenges.

Students must begin thinking about:

* Requirements
* Architecture
* Git/version control
* APIs
* Databases
* Testing
* Team communication
* Deployment
* Debugging
* Project planning

My industry and research-software experience has been particularly useful here because I can connect classroom concepts to the kinds of failures that appear in real systems.

For example, a system may:

* work locally but fail in production,
* pass unit tests but fail because of database state,
* have correct application logic but incorrect permissions,
* or appear to have an infrastructure problem when the real issue is application code.

I try to help students learn to investigate systems rather than guess at them.

# Capstone Project Mentoring

For **COM S 402C**, I worked with student teams developing real software projects.

My role included helping teams with:

* Project planning
* Requirement interpretation
* Milestone definition
* Progress tracking
* Software architecture
* Backend/API design
* Database design
* Cloud deployment
* Debugging
* Technical demonstrations

One recurring challenge is helping students translate a client's request into an implementable system.

A client may say:

> “We need users to upload files and process them.”

But the engineering questions underneath may include:

* Who can upload?
* Where are files stored?
* What happens if processing fails?
* How is job status represented?
* Who can see the results?
* How is access controlled?

I encourage students to uncover those hidden requirements before they become late-stage implementation problems.

# Mentoring Through Debugging

One of the most valuable teaching activities for me has been debugging with students.

Rather than immediately providing a corrected solution, I try to help students narrow down the problem.

For example:

```text
What did you expect?
      ↓
What actually happened?
      ↓
What is the smallest place the behavior diverges?
      ↓
What evidence do the logs / variables / tests provide?
      ↓
What hypothesis can we eliminate?
```

This is the same debugging process I use in research and production engineering.

Helping students develop that process is often more valuable than simply fixing one piece of code.

# Architecture and Code Reviews

I have also worked with students on code and design reviews.

Typical discussions include:

* Is this responsibility in the right component?
* Should this logic belong in the frontend or backend?
* Is this data duplicated unnecessarily?
* What happens if the API call fails?
* Can another user access this resource?
* Is this design easy to extend?
* What assumptions does this database relationship make?

These conversations help students move from writing code that works toward designing software that is understandable and maintainable.

# Teaching Across Different Student Levels

Working across introductory, advanced, and graduate courses has taught me that the same explanation does not work for every student.

An introductory student may first need:

> “What is an object?”

A senior software-engineering student may need:

> “Why should this object own this responsibility?”

A graduate researcher may need:

> “Is an object-oriented design even the right abstraction for this experiment?”

Teaching effectively requires understanding what level of abstraction the student is ready to reason about.

# Connecting Research and Teaching

My research also influences how I teach machine learning and software development.

For example, in computer vision, students may naturally focus on:

> Which model gives the highest accuracy?

My own research experience encourages additional questions:

* Was the train/test split appropriate?
* Is there subject leakage?
* What happens under domain shift?
* Are we evaluating the model on conditions it will actually encounter?
* Are preprocessing choices affecting the result?
* Does the model fail systematically for certain groups or conditions?

I want students to see experimentation as **reasoning**, not just model execution.

# My Teaching Philosophy in Practice

My teaching philosophy can be summarized around a few principles:

### Make students explain their reasoning

Correct output is useful, but understanding why the solution works is more important.

### Teach debugging as a core skill

Students should learn how to investigate unfamiliar failures rather than depend on trial and error.

### Connect concepts to real systems

APIs, databases, cloud services, Git, security, and deployment become easier to understand when students see how they interact in complete applications.

### Treat failure as part of learning

A failed deployment, incorrect model, or broken experiment can be more educational than an immediately successful result if the student understands why it failed.

### Build independence

The goal of mentoring is not for students to need the instructor indefinitely.

It is for them to develop the confidence and process required to solve increasingly unfamiliar problems on their own.
